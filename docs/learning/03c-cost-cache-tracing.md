# ‏שלב 3ג: עלות, cache ו-tracing

## ‏1. הבעיה

‏עד עכשיו, כל שאלה עלתה כסף ולקחה שניות, ואף אחד לא ידע כמה ולמה. בשלב הזה נוסיף שלושה דברים, ובכל אחד מהם **הקוד נכתב על ידך** בתרגיל TDD:

| ‏בעיה | ‏פתרון | ‏תרגיל |
|---|---|---|
| ‏"כמה עולה שאלה?" ו"מה אם הכסף נגמר?" | ‏עלות בדולרים בכל תשובה + תקציב יומי | ‏3ג-1 `SpendTracker` |
| ‏אותה שאלה נשאלת שוב ושוב | ‏cache של תשובות | ‏3ג-2 `AnswerCache` |
| ‏"זה היה איטי" ו"מה קרה לבקשה הזאת?" | ‏tracing: מזהה, זמן לכל שלב, שורת לוג אחת | ‏3ג-4 `Trace` |
| ‏חיבור של כולם בלי לשנות את ה-pipeline | ‏עטיפה (decorator) | ‏3ג-3 `GuardedPipeline` |

## ‏2. עלות לשאלה

‏Claude גובה לפי טוקנים, ומחיר טוקן שאתה שולח (input) שונה ממחיר טוקן שהוא כותב (output). ב-`usage` של כל תשובה יש את שם המודל ושני המספרים, אז העלות היא חישוב: `(input × מחיר_in + output × מחיר_out) / 1,000,000`.

‏הקוד ב-`src/rag/cost.py` (`PRICES`, `cost_usd`, `cost_of`). שאלה טיפוסית שלנו: כ-2,500 טוקנים פנימה ו-300 החוצה.

| ‏מודל | ‏עלות לשאלה | ‏כמה שאלות ב-5 דולר |
|---|---|---|
| ‏Haiku 5.5 | ‏≈ $0.0004 | ‏≈ 12,000 |
| ‏Sonnet 5.5 (ברירת המחדל) | ‏≈ $0.008 | ‏≈ 600 |
| ‏Opus 5.5 | ‏≈ $0.016 | ‏≈ 300 |

‏שים לב: הטוקנים של ה-thinking נספרים כ-output ונכללים כבר ב-`output_tokens`. מודל מקומי (Ollama) עולה 0 דולר, כי הוא לא ב-`PRICES`.

‏**מלכודת:** `cost_usd` מצפה למפתחות `input_tokens` ו-`output_tokens`. בבדיקות שבהן אין LLM אמיתי `usage` ריק, לכן `cost_of` מחזיר 0 כשאין usage. מקרה קצה כזה עולה בראיון.

## ‏3. תקציב יומי (`src/rag/spend.py`)

‏ה-rate limiter מגביל **בקשות** לדקה, לא **דולרים**. מפתח שדלף, או לולאה שגויה, יכולים לשרוף כסף בקצב "חוקי". `SpendTracker` הוא מפסק חשמלי לכסף: אחרי שהסכום של היום מגיע לתקציב, שאלות חדשות מקבלות **503** עד חצות UTC.

‏איך זה עובד: שומרים את "היום" (`שניות // 86400`) ואת הסכום עד כה. לפני כל קריאה בודקים אם היום התחלף, ואם כן מאפסים. השעון מוזרק (`clock`), ולכן אפשר לבדוק "מחר" בלי לחכות.

‏**שימו לב לשני דברים:**
- ‏**`threading.Lock`.** ‏FastAPI מריץ endpoint רגיל בכמה threads. `current_spend += cost` הוא שלושה צעדים (קרא, חבר, כתוב), ושני threads שנכנסים יחד מאבדים עדכון. ה-lock הופך את שלושת הצעדים לצעד אחד.
- ‏**מגבלה מוכרת:** התקציב חי בזיכרון של תהליך אחד. עם 3 containers ב-Cloud Run התקרה האמיתית היא פי 3. ב-production משתמשים ב-Redis משותף או בהתראות חיוב ברמת הפלטפורמה.

## ‏4. cache לתשובות (`src/rag/cache.py`)

‏תשובה עולה כסף ו-2 עד 5 שניות. אם כבר ענינו על אותה שאלה, עם אותו מודל ואותו אינדקס, מחזירים את התשובה השמורה: **0 דולר, בערך מילי-שנייה אחת**.

### ‏המפתח
‏`make_key(question, version)`: מנרמלים (אותיות קטנות, רווחים כפולים, פיסוק בסוף) ומצרפים את ה-`version`. ב-`api.py` ה-version הוא `מודל | גרסת תיעוד | top_k | מצב חיפוש`. **כל דבר שהתשובה תלויה בו צריך להיות במפתח**, אחרת שינוי שלו יחזיר תשובה ישנה. שימו לב מה *לא* במפתח: נוסח ה-system prompt, מודל ה-embedding והגדרות ה-chunking. שינוי באחד מהם דורש הפעלה מחדש, העלאת `docs_version` או המתנה ל-TTL.

### ‏פינוי
- ‏**TTL:** רשומה שגילה עבר `ttl` שניות פגה, וגם נמחקת (לא רק מוסתרת).
- ‏**LRU:** כשיש יותר מ-`max_items`, יוצאת הרשומה שהשתמשו בה הכי מזמן. `OrderedDict` מחזיק סדר, `move_to_end` מסמן "נעשה שימוש", ו-`popitem(last=False)` מוציא את הישנה.

## ‏5. החיבור: `GuardedPipeline` (`src/rag/guarded.py`)

‏מחלקה עם אותה שיטה כמו ל-`RAGPipeline` (`ask`), שעוטפת אותו (decorator). ה-pipeline לא משתנה, וה-API לא יודע שיש עטיפה.

<div dir="ltr">

```
1. cache hit?        -> מחזירים עותק עם cache_hit=True, cost_usd=0
2. התקציב נגמר?      -> BudgetExceeded  (ה-API עונה 503)
3. inner.ask(...)    -> הצעד היחיד שעולה כסף
4. מוסיפים עלות לסכום היום, שומרים ב-cache (לא "לא מצאתי")
5. מחזירים עותק עם cache_hit=False ו-cost_usd
```

</div>
‏**הסדר חשוב:** ה-cache נבדק לפני התקציב, כי hit לא עולה כלום, וגם כשהכסף נגמר שאלות שכבר נענו עדיין מוגשות.
‏**עותק, לא אובייקט שמור:** `dataclasses.replace` בונה עותק, כדי ששינוי אצל הקורא לא ישנה את מה שיושב ב-cache.

‏הגדרות (משתני סביבה): `ANSWER_CACHE_MAX_ITEMS` (500, ‏0 מכבה), `ANSWER_CACHE_TTL_SECONDS` (3600), `DAILY_BUDGET_USD` (5, ‏0 = בלי הגבלה).

## ‏6. tracing (`src/rag/trace.py`)

‏בלי trace, "זה היה איטי" הוא ניחוש. עם trace: החיפוש לקח 12ms ו-Claude 2,480ms, אז אין טעם לייעל את החיפוש.

‏`Trace` מכיל מזהה בקשה, `spans` (שם ← מילי-שניות), שדות נוספים (`set`), ו-`to_json()` שמחזיר **שורה אחת**:
<div dir="ltr">

```
{"request_id": "a3f9c1", "spans_ms": {"retrieve": 12.3, "generate": 2480.1}, "total_ms": 2495.0, "status": 200, "cache_hit": false, "cost_usd": 0.004, "model": "claude-sonnet-5-5", "cited": 3, "question_chars": 41}
```

</div>
‏שורה אחת לבקשה = אפשר `grep a3f9c1` ולראות את כל הסיפור, ואפשר להזין לכלי לוגים.

### ‏`span` כ-context manager
‏`with trace.span("retrieve"):` מודד את הבלוק. ה-`yield` ב-`@contextmanager` מחלק את הפונקציה: מה שלפניו רץ בכניסה, והבלוק שלך רץ בדיוק שם, ומה שאחריו (ב-`finally`) רץ ביציאה, **גם אם הבלוק זרק שגיאה**. לכן קריסה של Claude עדיין משאירה זמן מדוד בלוג.

### ‏`ContextVar`: איך ה-pipeline כותב ל-trace בלי לקבל אותו
‏`api.py` יוצר Trace לבקשה וקובע אותו כ"נוכחי" (`with tracing(trace)`). ב-`pipeline.py` יש `with span("retrieve"):` ו-`with span("generate"):`, הפונקציה `span` מחפשת את ה-trace הנוכחי, ואם אין (CLI, evals, בדיקות) היא לא עושה כלום. ‏`ContextVar` הוא משתנה שיש לו ערך נפרד לכל בקשה, כך ש-20 בקשות במקביל לא מתערבבות, ואין צורך להעביר `trace` דרך כל חתימת פונקציה.

### ‏מה אסור בלוג
- ‏**טקסט השאלה:** יכול להכיל מידע פרטי. אנחנו רושמים רק `question_chars`.
- ‏**מפתחות API וכותרות Authorization.**
- ‏**התשובה המלאה** (גדולה, ופרטית באותה מידה).

### ‏`X-Request-ID`
‏אם הקורא (או ה-load balancer) שלח את הכותרת, אנחנו שומרים אותה, וכך הלוגים שלהם ושלנו מתחברים. אחרת אנחנו יוצרים מזהה, ובכל מקרה מחזירים אותו בכותרת התשובה, גם ב-503. כשמשתמש מדווח על בעיה, הוא נותן מזהה ואתה מוצא את השורה.

### ‏OpenTelemetry
‏זה אותו רעיון בגרסה התעשייתית: מזהה, spans בעלי שם ומשך, ו-attributes, אבל נשלחים ל-Jaeger, Datadog או דומיהם, כולל מעקב בין שירותים. מי שבנה את הגרסה שלנו יכול להסביר אותו בראיון.

## ‏8. שאלות ראיון (תרגול)

<details><summary><b>‏מה בדיוק נכנס למפתח של ה-cache אצלנו, ומה *לא* נכנס?</b></summary>

‏המפתח הוא `השאלה המנורמלת | מודל|docs-גרסה|k<top_k>|מצב חיפוש`. הנרמול: אותיות קטנות, רווחים כפולים מאוחדים, וסימני `?.!` בסוף נמחקים. מה שלא במפתח: נוסח ה-system prompt, מודל ה-embedding והגדרות ה-chunking, ופרמטרים של ה-reranker. שינוי באחד מאלה לא מבטל תשובות שמורות, ולכן אחרי שינוי כזה מאתחלים את השירות או מעלים את `docs_version`, או מחכים ל-TTL (שעה).

‏זה מאזן בין דיוק לפשטות: אפשר לצרף hash של ה-prompt למפתח.
</details>

<details><summary><b>‏למה אנחנו לא משתמשים ב-semantic cache, ומתי כן היה שווה?</b></summary>

‏cache סמנטי מחזיר תשובה לשאלה *דומה*, אבל דמיון ב-embedding לא אומר אותה משמעות: "make the parameter optional" ו-"make the parameter required" כמעט זהות, ותשובותיהן הפוכות. במערכת שעונה על תיעוד טכני, תשובה שגויה במקום תשובה איטית פוגעת באמון. אצלנו גם פספוס cache עולה סנטים בלבד.

‏זה היה שווה במערכת עם נפח גבוה מאוד של שאלות חוזרות בניסוחים שונים וסיכון נמוך לטעות (למשל שאלות נפוצות של שירות לקוחות), עם סף דמיון שמכוילים מול דוגמאות אמיתיות.
</details>

<details><summary><b>‏אילו תשובות לא שומרים ב-cache, ולמה?</b></summary>

‏לא שומרים "לא מצאתי" ולא תשובה בלי מקורות. כיום זה בקוד: `answer.text != NOT_FOUND and answer.sources`. הסיבה: "לא מצאתי" יכול לנבוע מפספוס זמני של החיפוש או מאינדקס שעוד לא נטען, ושמירה שלו תגיש את הכישלון לכולם עד שה-TTL יפוג. שגיאות (קריאה שנכשלה) בכלל לא מגיעות לשמירה, כי `inner.ask` זורק חריגה לפני כן.
</details>

<details><summary><b>‏למה ה-cache נבדק לפני בדיקת התקציב, ומה היה קורה בסדר ההפוך?</b></summary>

‏cache hit לא עולה כסף, ולכן אין סיבה לחסום אותו כשהתקציב נגמר. בסדר ההפוך, אחרי חצות הדולר האחרון כל שאלה, כולל כאלה שכבר ענינו עליהן, הייתה מקבלת 503, והשירות היה נראה מת למרות שיכול לענות על חלק מהתנועה. בסדר שלנו: שאלות חדשות נחסמות, ושאלות שכבר נענו ממשיכות לקבל תשובה.
</details>

<details><summary><b>‏האם התקציב היומי מבטיח שלא נוציא יותר מ-5 דולר ביום?</b></summary>

‏לא. הבדיקה (`allow`) נעשית *לפני* הקריאה, והעלות נרשמת (`record`) *אחרי*. לכן בקשה שמתחילה כשנשארו 0.001 דולר עוברת, וגם כמה בקשות במקביל יכולות לעבור את הבדיקה לפני שאחת מהן נרשמה. החריגה המקסימלית היא בערך עלות כל הבקשות שבטיסה בו-זמנית (אצלנו סנטים בודדים). וגם: התקציב לכל תהליך, אז עם N containers התקרה היא N × התקציב.

‏אם צריך תקרה קשיחה: מקצים (reserve) הערכת עלות לפני הקריאה ומתקנים אחריה, ובנוסף שמים התראת חיבור בפלטפורמה.
</details>

<details><summary><b>‏איזה באג יש ב-`current_spend += cost` כשכמה threads רצים, ואיך מתקנים?</b></summary>

‏הפעולה היא שלושה צעדים: קריאת הערך, חיבור, כתיבה. שני threads שקוראים את אותו ערך מתחילתו, כל אחד מוסיף את העלות שלו וכותב, והעדכון של אחד נאבד (lost update), כך שהתקציב נספר בחסר. FastAPI מריץ endpoint רגיל (`def`) ב-thread pool, ולכן זה קורה באמת. פתרון: `threading.Lock` שעוטף את שלושת הצעדים (`with self._lock:`) כך שרק thread אחד בתוכם.

‏אותו עיקרון חל על `AnswerCache` ועל `RateLimiter`. ב-async אין צורך ב-lock בין `await`ים, אבל הקוד שלנו סינכרוני.
</details>

<details><summary><b>‏למה שורת לוג JSON אחת לבקשה, ומה לא רושמים בה?</b></summary>

‏שורה אחת מכילה את כל הסיפור של בקשה (`request_id`, משכי ה-spans, זמן כולל, עלות, `cache_hit`, סטטוס), כך ש-`grep request_id` מספיק, והיא ניתנת לקריאה ע"י כלי לוגים ללא ניתוח טקסט חופשי. לא רושמים: את טקסט השאלה (יכול להכיל מידע אישי; רושמים רק `question_chars`), את התשובה המלאה, מפתחות API וכותרות `Authorization`, ופרטי משתמשים או תשלום.

‏אפשר ללמוד מהמטא-דאטה (אורך, זמן, עלות) מה קרה בלי לחשוף את התוכן.
</details>

<details><summary><b>‏איך ה-pipeline כותב ל-trace בלי לקבל אותו כפרמטר, ולמה זה בטוח כשיש בקשות במקביל?</b></summary>

‏`api.py` קובע trace נוכחי בעזרת `ContextVar` (`with tracing(trace)`), ו-`span("retrieve")` בתוך `pipeline.py` מחפש אותו. אם אין trace (CLI, evals, בדיקות) הוא פשוט לא עושה כלום. `ContextVar` נותן לכל בקשה (לכל thread או task) ערך משלה, ולכן 20 בקשות במקביל לא כותבות ל-trace של אחרת. המחיר: זה "מצב נסתר": קשה יותר לראות מהחתימה שהפונקציה כותבת ל-trace.
</details>
