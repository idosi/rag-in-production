# ‏שלב 2א: מודדים את ה-retrieval

> ‏המטרה של השלב: להפוך את "נראה לי שזה עובד" למספר. לפני שמשנים משהו ב-retrieval, צריך לדעת איפה אנחנו עומדים, כדי שכל שינוי יימדד מול אותו קו בסיס.

## ‏1. למה למדוד, ולמה דווקא retrieval קודם

‏בתרגיל 1 ראינו שהשאלה "How do I run code after returning a response?" נכשלה. ה-LLM התנהג מצוין, אבל העמוד הנכון (Background Tasks) פשוט לא הגיע ל-top 5. **אם המקור הנכון לא הגיע, אף מודל ואף פרומפט לא יתקנו את התשובה.**

‏אנלוגיה: retrieval הוא הספרן, וה-LLM הוא המומחה. אם הספרן מביא את הספרים הלא נכונים, להחליף את המומחה במומחה יקר יותר לא יעזור. קודם מודדים ומתקנים את הספרן.

‏**ועוד סיבה מעשית:** מדידת retrieval היא **חינם ודטרמיניסטית**. לא קוראים ל-LLM, הריצה לוקחת שניות, ואותה הרצה תמיד נותנת אותה תוצאה. לעומת זאת, מדידת תשובות (שלב 2ג) עולה כסף, וה-LLM לא תמיד עונה אותו דבר.

## ‏2. ה-golden set

‏הקובץ `evals/golden_set.json` מכיל 47 שאלות. לכל שאלה רשומים הסעיפים בתיעוד שעונים עליה:

<div dir="ltr">

```json
{"id": "q03", "category": "paraphrase",
 "question": "How do I run code after returning a response?",
 "relevant": ["tutorial/background-tasks#background-tasks",
              "tutorial/background-tasks#using-backgroundtasks"]}
```

</div>

‏**החלטות התכנון, וכל אחת למה:**

| ‏החלטה | ‏למה |
|---|---|
| ‏התיוג הוא לפי **סעיף** (`page#anchor`) ולא לפי chunk id | ‏מספרי ה-chunks משתנים כשמשנים את `CHUNK_SIZE`, והעוגנים של הסעיפים לא. ככה אותו סט יכול להשוות גם הגדרות chunking שונות |
| ‏כמה סעיפים "נכונים" לשאלה | ‏לרוב יש יותר ממקום אחד בתיעוד שעונה על השאלה. אסור להעניש את החיפוש על כך שמצא תשובה נכונה אחרת |
| ‏**קטגוריות** | ‏ממוצע כללי מסתיר דפוסים. נרצה לראות, למשל, ש-hybrid search משפר בעיקר את `code-name` |
| ‏שאלות `unanswerable` | ‏לא משתתפות במדידת retrieval (אין להן סעיף נכון). הן חשובות לשלב 2ג, כדי לבדוק שהמערכת אומרת "לא יודע" |
| ‏טסט שבודק שכל העוגנים קיימים בקורפוס | ‏אם נעדכן את גרסת התיעוד ועוגן ישתנה, הטסט ייכשל במקום שה-eval יתחיל לשקר בשקט |

‏**הקטגוריות:**

| ‏קטגוריה | ‏מה היא בודקת | ‏דוגמה |
|---|---|---|
| ‏`direct` | ‏השאלה משתמשת במילים של התיעוד | ‏How do I read a cookie? |
| ‏`paraphrase` | ‏ניסוח של משתמש אמיתי, במילים אחרות | ‏How do I serve images and CSS files from a folder? |
| ‏`code-name` | ‏שם מדויק של פונקציה או פרמטר | ‏What does `response_model_exclude_unset` do? |
| ‏`multi` | ‏התשובה מפוזרת על כמה סעיפים | ‏protect an endpoint and get the current user |
| ‏`unanswerable` | ‏אין תשובה בקורפוס | ‏How do I use WebSockets? |

‏**הסתייגות כנה:** את הסט כתבתי אני, והוא מכיל 47 שאלות. זה מספיק כדי לזהות שינויים גדולים, אבל לא שינויים של 1 עד 2 אחוזים: שאלה אחת שווה בערך 2.4% מהציון. ב-production, הסט גדל משאלות אמיתיות של משתמשים (מהלוגים, בשלב 3).

## ‏3. המדדים

| ‏מדד | ‏מה הוא אומר | ‏למה צריך אותו |
|---|---|---|
| ‏**hit@k** | ‏באיזה אחוז מהשאלות לפחות סעיף נכון אחד נמצא ב-top k | ‏**hit@5 הוא המספר הראשי**, כי 5 chunks הם מה שה-LLM מקבל |
| ‏**recall@k** | ‏איזה חלק מ**כל** הסעיפים הנכונים נמצא ב-top k | ‏חשוב לשאלות `multi`, שבהן סעיף אחד לא מספיק |
| ‏**MRR** | ‏ממוצע של 1 חלקי המיקום של הפגיעה הראשונה (0 אם אין פגיעה) | ‏מתגמל את החיפוש על כך שהתשובה הנכונה נמצאת **ראשונה**, ולא רק איפשהו ב-top 5 |

‏**דוגמה לחישוב** (מתוך ה-docstring של `score_question`): הסעיפים הנכונים הם A ו-B, ונמצאו `[X, A, A, Y, B]`:
- ‏הפגיעה הראשונה במקום 2, ולכן reciprocal rank = ½
- ‏hit@1 = לא, ‏hit@3 = כן
- ‏recall@3 = ½ (נמצא A, אבל B רק במקום 5), ו-recall@5 = 1

‏**למה hit@10 גם מעניין:** אם hit@10 גבוה בהרבה מ-hit@5, הסעיף הנכון נמצא אבל מדורג נמוך מדי. זה בדיוק המצב ש-**reranker** פותר: מושכים יותר מועמדים ומדרגים אותם מחדש.

## ‏4. איך מריצים וקוראים את התוצאה

<div dir="ltr">

```
make eval-retrieval
```

</div>

‏הפלט: טבלה לפי קטגוריה, רשימה של כל השאלות שפספסו ב-k=5 ומה הגיע במקומן, וקובץ JSON ב-`evals/results/`. הקובץ שומר גם את ההגדרות שבהן ההרצה בוצעה (מודל embedding, גודל chunk). השוואה בין שתי הרצות בלי לדעת מה השתנה ביניהן לא שווה כלום.

‏**איך קוראים רשימת misses:** לכל פספוס כתוב באיזה מקום הופיעה הפגיעה הראשונה ומה הגיע במקום. שני מצבים שונים מאוד:
- ‏כשכתוב **"first hit at rank 7"**: החיפוש מצא את הסעיף אבל דירג אותו נמוך. ‏**reranker** יעזור.
- ‏כשכתוב **"not in top 10"**: החיפוש לא מצא אותו בכלל. צריך **hybrid search**, מודל embedding אחר או ניסוח מחדש של השאלה.

## ‏5. תרגיל

1. ‏`git pull` ואז `make eval-retrieval`. **זה ה-baseline שלנו.** תדביק לי את הטבלה ואת רשימת ה-misses.
2. ‏לפני שאתה מסתכל: באיזו קטגוריה אתה מנחש שהציון יהיה הכי נמוך, ולמה? אחר כך תבדוק אם צדקת.
3. ‏תעבור על 3 misses ותבדוק: האם התיוג שלי נכון? (יכול להיות שהחיפוש מצא סעיף שגם הוא עונה, ושכחתי לתייג אותו.) **eval עם תיוג שגוי מטעה יותר מאשר בלי eval בכלל.**
4. ‏`git add evals/results && git commit`. התוצאות נשמרות בריפו, ככה שאפשר להראות את ההתקדמות לאורך הפרויקט.

## ‏6. שאלות ראיון

<details><summary><b>‏איך מודדים איכות של RAG?</b></summary>
‏בנפרד ל-retrieval ול-generation. ל-retrieval: golden set של שאלות עם המקורות הנכונים, ומדדים כמו hit@k, ‏recall@k ו-MRR. זה זול ודטרמיניסטי. ל-generation: faithfulness (התשובה מגובה במקורות), correctness וסירוב נכון, לרוב עם LLM-as-judge ובדיקה ידנית של מדגם. מפרידים כי כל כשל דורש תיקון אחר.
</details>

<details><summary><b>‏מה ההבדל בין hit@k ל-recall@k?</b></summary>
‏hit@k שואל אם נמצא לפחות מקור נכון אחד, וזה מספיק לרוב השאלות. ‏recall@k שואל איזה חלק מכל המקורות הנכונים נמצא, וזה חשוב כשהתשובה מפוזרת על כמה מקומות.
</details>

<details><summary><b>‏למה MRR ולא רק hit@k?</b></summary>
‏hit@5 לא מבחין בין "הנכון ראשון" ל"הנכון חמישי". MRR כן. זה חשוב כי LLMs נותנים יותר משקל למה שמופיע מוקדם בהקשר, וכי עם MRR גבוה אפשר אולי להוריד את k ולחסוך טוקנים.
</details>

<details><summary><b>‏מאיפה מביאים golden set ב-production?</b></summary>
‏מתחילים מסט ידני קטן (כמו שלנו). אחר כך מוסיפים שאלות אמיתיות מהלוגים, במיוחד כאלה שקיבלו פידבק שלילי או סירוב. אפשר גם לייצר שאלות סינתטיות עם LLM מתוך ה-chunks, אבל צריך לבדוק אותן, כי הן נוטות להעתיק את הניסוח של המסמך ולכן קלות מדי.
</details>

<details><summary><b>‏למה לתייג לפי סעיף ולא לפי chunk?</b></summary>
‏כי ה-chunks משתנים כשמשנים את אסטרטגיית ה-chunking, וזה בדיוק אחד הדברים שרוצים להשוות. תיוג לפי יחידה יציבה (סעיף או עמוד) מאפשר להשוות בין הגדרות.
</details>
