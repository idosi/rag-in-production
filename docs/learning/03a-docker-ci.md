# ‏שלב 3א: Docker ו-CI

> ‏המטרה: שהמערכת תרוץ אותו דבר על כל מחשב, ושכל שינוי בקוד ייבדק אוטומטית לפני שהוא נכנס.

## ‏1. שתי בעיות, שני פתרונות

- ‏**"אצלי זה עובד".** גרסת Python, גרסאות של חבילות, מודלים שצריך להוריד, משתני סביבה. **קונטיינר** (Docker) אורז את כל אלה לתמונה אחת (image) שרצה אותו דבר בכל מקום: המחשב שלך, שרת, Cloud Run.
- ‏**"שברתי משהו ולא שמתי לב".** ‏**CI** (Continuous Integration) מריץ בדיקות אוטומטית על כל push ועל כל PR, על מכונה נקייה שאין בה שום דבר ממה שיש אצלך.

‏אנלוגיה: הקונטיינר הוא ארוחה ארוזה במגש עם כל המצרכים. ה-CI הוא בודק איכות שפותח כל מגש לפני שהוא יוצא מהמטבח.

## ‏2. ה-Dockerfile, ארבעה רעיונות

‏הקובץ `Dockerfile` מלא בהערות, וכאן העיקר:

- ‏**Multi-stage:** שלושה שלבים (`builder`, `models`, `runtime`). רק האחרון נשלח. בשלב הראשון יש את `uv` וכלי הבנייה, והם לא צריכים להיות בתמונה שרצה בפרודקשן. תמונה קטנה יותר היא פריסה מהירה יותר ושטח תקיפה קטן יותר.
- ‏**סדר השכבות והמטמון:** כל פקודה היא שכבה, ו-Docker משתמש מחדש בשכבה אם שום דבר לפניה לא השתנה. לכן קודם מעתיקים רק `pyproject.toml` ו-`uv.lock` ומתקינים תלויות (איטי, משתנה לעתים רחוקות), ורק אחרי זה את הקוד (משתנה כל הזמן). בלי הסדר הזה כל שינוי של שורה אחת היה מתקין הכול מחדש.
- ‏**המודלים נאפים בזמן build:** שני מודלי ה-ONNX (כ-200MB) יורדים פעם אחת בבנייה, ולא בכל הפעלה של קונטיינר. הקונטיינר לא תלוי ב-Hugging Face בזמן עלייה, וגם עולה מהר יותר.
- ‏**משתמש רגיל, לא root:** אם מישהו מנצל פרצה באפליקציה, הוא לא מקבל הרשאות root בתוך הקונטיינר.

‏`uv sync --frozen` מתקין **בדיוק** את מה שב-`uv.lock` ונכשל אם הקובץ לא מעודכן. זו אותה הבטחה שנותן `package-lock.json` או `Pipfile.lock`: מה שבדקנו הוא מה שירוץ.

## ‏3. docker-compose, שלוש הערות

- ‏**`profiles: ["app"]`:** שירות ה-API לא עולה עם `make up` (שמריץ רק Postgres, לפיתוח מקומי כמו קודם). הוא עולה עם `make docker-up`.
- ‏**`DATABASE_URL` עם `db` ולא `localhost`:** בתוך רשת ה-compose שם השירות הוא כתובת ה-host. `localhost` בתוך קונטיינר הוא הקונטיינר עצמו. הערך ב-`environment` גובר על `.env`, כדי שכתובת localhost מהקובץ לא תשבור את זה.
- ‏**`.env` לא בתוך התמונה:** `.dockerignore` מוציא אותו. מפתח API בתוך שכבה של תמונה הוא מפתח שדלף, ואי אפשר למחוק אותו משם אחר כך. המפתח נכנס בזמן ריצה בלבד, דרך `env_file`.

## ‏4. ה-CI (`.github/workflows/ci.yml`)

‏שני jobs עצמאיים, כדי שכשל של Docker וכשל של בדיקות יופיעו בנפרד:

- ‏**`test`:** מרים Postgres עם pgvector (אותה תמונה כמו ב-compose), מתקין עם `uv sync --frozen`, מריץ ‏`ruff check`, ‏`ruff format --check` ו-`pytest`. הבדיקות רצות מול מסד נתונים אמיתי, לא מדומה.
- ‏**`docker`:** בונה את התמונה (בלי להעלות אותה לשום מקום), כדי לגלות שהיא נשברה לפני ה-merge.

‏**הגנות קטנות שחשוב להכיר:** `permissions: contents: read` (הטוקן של ה-workflow יכול רק לקרוא, כלל least privilege), ו-`concurrency` שמבטל ריצה ישנה כש-push חדש מגיע.

‏**מה בכוונה לא ב-CI:** ה-evals (`make eval-*`). הם קוראים ל-API בתשלום וגם לוקחים דקות. מריצים אותם ידנית כשמחליפים מודל, פרומפט או הגדרות חיפוש. ובדיקות ה-CI לא צריכות מפתח API בכלל.

## ‏5. מה לא נבדק, ומה עוד חסר

‏**בסביבה שבה כתבתי את זה אין Docker daemon ואין גישה ל-Hugging Face, אז:**
- ‏**התמונה לא נבנתה על ידי.** בדקתי ש-`docker compose config` תקין, שה-YAML של ה-workflow תקין, ושרצף הפקודות של `uv sync` עובד ומתקין את החבילה בלי תלויות פיתוח. את הבנייה האמיתית אתה מריץ ראשון.
- ‏**ה-workflow לא רץ עדיין.** הוא ירוץ על ה-PR הזה, ושם נראה אם הוא ירוק.

‏**חוסרים שאני מכיר, ואפשר להוסיף בהמשך:**
- ‏נעיצת ה-actions לפי SHA במקום גרסה (`@v4`): תג יכול לזוז, SHA לא. זו הגנה מפני תקיפת שרשרת אספקה.
- ‏סריקת הקונטיינר לפגיעויות (Trivy) ב-CI.
- ‏`HF_HUB_OFFLINE=1` בקונטיינר, כדי שהוא ייכשל בקול אם מודל חסר ולא ינסה להוריד. לא הוספתי כי לא יכולתי לוודא ש-fastembed מתנהג איתו נכון.
- ‏פרסום התמונה ל-registry ופריסה: זה שלב הענן (3ב).

## ‏6. תרגיל

```
git fetch && git checkout step-3a-docker-ci
make docker-up          # builds the image (slow the first time), starts db + api
make docker-ingest      # fills the index from inside the container
curl localhost:8000/health
docker images           # how big is the image?
docker history rag-in-production-api    # which layer is the heaviest?
```

1. ‏**תדביק לי** את הגודל של התמונה ואת השכבה הכבדה ביותר.
2. ‏**שנה שורה אחת בקוד** (למשל הערה ב-`api.py`) והרץ שוב `make docker-build`. אילו שכבות נבנו מחדש, ואילו הגיעו מהמטמון? זה מוכיח שהבנת את סדר השכבות.
3. ‏**שבור בכוונה** בדיקה אחת, דחוף, ותראה את ה-CI נהיה אדום ב-PR.

## ‏7. שאלות ראיון

<details><summary><b>‏למה multi-stage build?</b></summary>
‏כדי שהתמונה הסופית תכיל רק את מה שצריך כדי להריץ: בלי כלי בנייה, בלי caches. תמונה קטנה יותר נפרסת מהר יותר ומכילה פחות קוד שעלול להכיל פגיעויות.
</details>

<details><summary><b>‏למה מעתיקים את קובץ התלויות לפני הקוד?</b></summary>
‏בגלל מטמון השכבות של Docker. שכבה נבנית מחדש רק אם משהו לפניה השתנה. תלויות משתנות לעתים רחוקות וקוד משתנה כל הזמן, אז מפרידים ביניהם כדי שכל עריכה של קוד לא תפעיל התקנה מחדש.
</details>

<details><summary><b>‏מה לא שמים ב-CI של מערכת עם LLM?</b></summary>
‏קריאות אמיתיות ל-API (איטי, יקר, ולא דטרמיניסטי). ב-CI בודקים עם fakes. את ה-evals מריצים בנפרד, לפני שינוי של מודל, פרומפט או חיפוש, ושומרים את התוצאות.
</details>

<details><summary><b>‏איך אתה מוודא שמפתח API לא נכנס לתמונה?</b></summary>
‏`.dockerignore` שמוציא את `.env`, מפתח שמוזרק בזמן ריצה בלבד (משתנה סביבה או secret manager), ובדיקה אוטומטית שמוודאת ש-`.env` ב-`.dockerignore` ושאין `COPY .env`. מפתח בשכבה של תמונה לא ניתן למחיקה.
</details>
