# ‏סיכום מלא: כל מה שבנינו, וכל מה שלמדנו

‏המסמך הזה עובר על הפרויקט שלב אחרי שלב. לכל שלב חמישה חלקים קבועים: מה בנינו, למה, ההחלטות והמחיר שלהן, המספרים האמיתיים, והטעויות שעשינו בדרך. כל מספר כאן לקוח מהמדריך של אותו שלב (הקישור בכותרת), ואם יש סתירה, המדריך קובע.

‏איך להשתמש בו: לקרוא שלב, לסגור את המסך, ולהסביר אותו בקול בשתי דקות. אם נתקעת, חזור למדריך של השלב. החידון ב-[06](06-quiz.md) בודק בדיוק את החומר הזה, ושאלות הראיון ב-[07](07-interview-questions.md) בונות עליו.

## ‏תמונת על בשלוש שורות

‏הבעיה: RAG שנראה מצוין בדמו ונכשל בשאלה הראשונה של משתמש אמיתי. התשובה שלנו: קודם סרגל (golden set ושני evals), אחר כך כל שינוי נמדד מולו, ורק אחר כך העולם האמיתי (כסף, תוקפים, ענן, תקלות). המשפט שמחבר הכול: **אל תנחש, תמדוד.**

<div dir="ltr">

```
OFFLINE  (make ingest):  48 FastAPI pages -> chunker (headings, ~1200 chars)
                         -> bge-small (384d) -> Postgres + pgvector (745 chunks)

ONLINE   (POST /ask):    422? -> X-API-Key 401 -> rate limit 429 -> trace starts
                         -> cache hit? ($0) -> budget left? (503)
                         -> embed -> pgvector top 10 -> cross-encoder rerank -> top 5
                         -> Claude Sonnet 5.5, sources-only prompt -> answer + [n]
                         -> cost_usd, cache store, one JSON trace line

CLOUD:   GitHub push -> CI (ruff, pytest on real pgvector, docker build)
         -> CD (WIF, no key) -> Cloud Run revision with no traffic -> smoke -> traffic
         Cloud Run (Frankfurt) <-> Neon Postgres (Frankfurt), secrets in Secret Manager
         log-based metrics -> 3 alerts (errors, p95 latency, budget) -> email
```

</div>

## ‏שלב 0: מפת הקוד ([00](00-code-map.md))

**‏מה:** מדריך קריאה של שעה. שני סיפורים: ingest (בניית האינדקס) ו-ask (שאלה), ושלושה סיפורי עזר (API, evals, ‏Docker ו-CI).

**‏הרעיון שכדאי לזכור:** כל קובץ אחראי על דבר אחד. `store.py` לא יודע מה זה Claude, ו-`generator.py` לא יודע מה זה SQL. זה מה שאפשר אחר כך להחליף reranker, מודל או מסד נתונים בלי לגעת בשאר.

**‏סדר הבדיקות בבקשה:** הזולות קודם והיקרה אחרונה: 422, ‏401, ‏429, ‏cache, ‏503 של התקציב, חיפוש, ורק אז Claude.

## ‏שלב 1: הבסיס ([01](01-foundations.md))

**‏מה בנינו:** מערכת שעובדת מקצה לקצה: loader, ‏chunker, ‏embeddings, ‏Postgres עם pgvector, ‏generator עם ציטוטים, ‏pipeline ו-API.

**‏למה RAG ולא fine-tuning:** fine-tuning מלמד סגנון והתנהגות. RAG מוסיף ידע שאפשר לעדכן (ingest מחדש) ולצטט. אנלוגיה: ספרן שמביא 5 עמודים, ומומחה שעונה רק מהם.

**‏ההחלטות והמחיר:**

| ‏החלטה | ‏למה | ‏המחיר |
|---|---|---|
| ‏קורפוס נעוץ לגרסה 0.162.0 | ‏בלי דאטה יציב אין מדידה: ציון שירד לא יגיד אם הקוד התקלקל או הדאטה השתנה | ‏לא מתעדכן לבד |
| ‏שיבוץ קוד הדוגמאות בתוך הטקסט | ‏בתיעוד של FastAPI הקוד הוא הפניה (`{* ... *}`). בלי שיבוץ, תשובות "איך עושים" בלי קוד | ‏loader מורכב יותר |
| ‏chunking לפי כותרות Markdown, עד 1,200 תווים, ‏overlap של 200, נתיב כותרות בראש כל chunk | ‏לא חותך קוד באמצע, וכל chunk יודע על מה הוא | ‏1,200 הוא ניחוש מושכל, לא מדידה |
| ‏`bge-small-en-v1.5` מקומי דרך fastembed, ‏384 מימדים | ‏בלי מפתח, בלי עלות לקריאה, הדאטה לא יוצא | ‏מודלים בתשלום בדרך כלל טובים יותר |
| ‏`embed_query` ו-`embed_documents` נפרדים | ‏BGE אסימטרי: לשאלה יש prefix | ‏שימוש באותה פונקציה מוריד איכות בשקט |
| ‏Postgres + pgvector, אינדקס HNSW, ‏`vector_cosine_ops` עם `<=>` | ‏מערכת אחת לטקסט, metadata ווקטורים | ‏בעשרות מיליונים צריך לכוונן או לעבור |
| ‏ingest אידמפוטנטי: hash של תוכן **והגדרות** (chunk size, overlap, מודל) | ‏הרצה חוזרת בטוחה, שינוי הגדרה מכריח בנייה מחדש | ‏— |
| ‏החלפת דף בטרנזקציה אחת, ומחיקת דפים שנעלמו (אבל לא אם ה-loader החזיר 0) | ‏קורא לא רואה חצי דף, ודף שנמחק לא מצוטט לנצח | ‏— |
| ‏system prompt של "רק מהמקורות", ‏`[n]`, ומשפט NOT_FOUND קבוע | ‏grounding, אפשר לאמת ולמדוד | ‏— |
| ‏`parse_citations` זורק מספרים מחוץ לטווח | ‏`[7]` כשיש 5 מקורות הוא ציטוט מומצא | ‏— |
| ‏endpoint הוא `def` ולא `async def` | ‏הקריאות חוסמות, אז FastAPI מריץ ב-thread pool | ‏חיבור DB אחד משותף לכל ה-threads |
| ‏`if not sources` לפני Claude | ‏לא משלמים על קריאה שבטוח תיכשל | ‏אינדקס ריק נראה כמו "לא מצאתי" רגיל |

**‏המספרים:** ‏43 דפים, ‏661 chunks בהתחלה, חציון 707 תווים, ‏32 chunks קטנים מ-150 תווים. ההרצה הראשונה על ה-Mac: ציון עליון 0.826, ‏4 מתוך 5 מקורות צוטטו, ‏2,311 טוקנים פנימה ו-312 החוצה.

**‏התובנה הכי חשובה של השלב:** ציון similarity לא יודע אם יש תשובה. "deploy to Kubernetes" (אין תשובה) קיבלה 0.765, יותר מ-"run code after returning a response" (יש תשובה, החיפוש פספס) עם 0.729. לכן אין סף על הציון, והסירוב הוא תפקיד המודל, והוא נמדד.

**‏הטעויות שלנו:**
- ‏ה-ingest הדפיס 661 chunks והטבלה הייתה ריקה: psycopg עם `autocommit=False` הפך את `conn.transaction()` ל-savepoints שאף פעם לא נשמרו. התיקון: `autocommit=True`, וטסט שקורא **מחיבור שני**. הלקח: טסט persistence חייב לקרוא דרך חיבור אחר.
- ‏הטסטים מחקו את האינדקס של הפיתוח. התיקון: מסד `rag_test` נפרד.
- ‏‏401 בהרצה הראשונה: מפתח חסר ב-`.env`.

## ‏שלב 2א: מודדים את החיפוש ([02א](02a-retrieval-evals.md))

**‏מה בנינו:** `evals/golden_set.json` (בהתחלה 47 שאלות: 42 עם תשובה ו-5 בלי) ו-`make eval-retrieval`.

**‏למה החיפוש קודם:** אם הספרן מביא את הספרים הלא נכונים, מומחה יקר יותר לא יעזור. ובנוסף, eval של חיפוש הוא חינם ודטרמיניסטי.

**‏ההחלטות:**
- ‏תיוג לפי **סעיף** (`page#anchor`) ולא לפי chunk, כדי שאפשר יהיה להשוות הגדרות chunking שונות על אותו סט.
- ‏כמה סעיפים נכונים לשאלה, כדי לא להעניש תשובה נכונה אחרת.
- ‏קטגוריות (`direct`, ‏`paraphrase`, ‏`code-name`, ‏`multi`, ‏`unanswerable`), כי ממוצע מסתיר דפוסים.
- ‏טסט שבודק שכל עוגן קיים בקורפוס, כדי שה-eval לא ישקר בשקט אחרי עדכון גרסה.
- ‏תיוגים קפואים: לא משנים תיוג כדי ששאלה תעבור.

**‏המדדים:** ‏hit@k (לפחות סעיף נכון אחד ב-top k, המספר הראשי ב-k=5), ‏recall@k (איזה חלק מכל הסעיפים הנכונים), ‏MRR (ממוצע של 1 חלקי מיקום הפגיעה הראשונה).

**‏המספרים (בסיס, vector, ‏42 שאלות):** ‏hit@5 ‏0.905, ‏recall@5 ‏0.722, ‏MRR ‏0.759. ‏recall@5 של `direct` רק 0.632, כי chunks מאותו סעיף תופסים כמה מ-5 המקומות.

**‏הסתייגות שחשוב להגיד:** שאלה אחת שווה כ-2.4 נקודות אחוז. הפרש של שאלה או שתיים הוא רעש, ולכן מסתכלים על fixed ו-broke.

## ‏שלב 2ב: ‏hybrid ו-reranker ([02ב](02b-hybrid-search-rerank.md))

**‏מה בנינו:** חיפוש מילים בתוך Postgres (עמודת `tsv` מסוג `GENERATED ... STORED` עם אינדקס GIN, משקל A לכותרת ו-B לגוף, שאילתת OR), מיזוג RRF, ‏cross-encoder reranker, וארבעה מצבים שנמדדים כל אחד לחוד.

**‏למה ארבעה מצבים:** כל מצב מוסיף רעיון אחד. אם בונים רק `hybrid_rerank`, לא יודעים איזה חצי עזר, ואולי אחד מהם בכלל מזיק.

**‏RRF:** ‏`score = Σ 1/(60 + rank)`. מתעלם מהציונים (cosine בין 0.70 ל-0.85, ‏ts_rank_cd בין 0.01 ל-2, מטרים מול שקלים) ומשתמש רק במיקום.

**‏bi-encoder מול cross-encoder:** הראשון מקודד שאלה ומסמך בנפרד, אז אפשר לחשב מראש ולחפש באינדקס. השני קורא את שניהם יחד, מדויק יותר, אבל רץ על כל זוג. אנלוגיה: סינון קורות חיים מול ראיון.

**‏התוצאות (42 שאלות, top 5, על ה-Mac):**

| ‏מצב | ‏hit@5 | ‏MRR | ‏p50 | ‏תיקן / שבר מול vector |
|---|---|---|---|---|
| ‏vector | ‏0.905 | ‏0.759 | ‏8ms | |
| ‏hybrid | ‏0.905 | ‏0.719 | ‏11ms | ‏q27 / ‏q39 |
| ‏rerank MiniLM, ‏30 מועמדים | ‏0.881 | ‏0.720 | ‏620ms | ‏3 / ‏4 |
| ‏rerank ‏bge-reranker-base, ‏30 | ‏0.952 | ‏0.793 | ‏2,928ms | ‏3 / ‏1 |
| ‏**rerank MiniLM, ‏10 מועמדים** | ‏**0.952** | ‏0.746 | ‏163ms | ‏q03 q27 / **אף אחת** |

**‏ההחלטה:** `RETRIEVAL_MODE=rerank`, ‏`CANDIDATE_K=10`.

**‏למה פחות מועמדים יצא גם טוב יותר:** ה-reranker יכול רק לסדר מחדש את מה שקיבל. ב-10 הראשונים החיפוש הווקטורי כבר טוב, ולכן ה-reranker לא יכול להעלות chunk שגוי שהיה במקום 25. המגבלה היא שמגינה.

**‏למה hybrid לא עזר:** ‏`ts_rank_cd` הוא לא BM25, אין לו IDF. ב-q39 ("images and CSS files") המילה הנפוצה "files" גררה את דף העלאת הקבצים. והשאלות שלנו בשפה טבעית, לא קודי שגיאה.

**‏מה נשאר פתוח:** ‏q18 (model בתוך model) ו-q22 (להסתיר password) נכשלות. זה פער של אוצר מילים, לא של דירוג.

## ‏שלב 2ג: מודדים תשובות ובוחרים מודל ([02ג](02c-answer-evals.md))

**‏מה בנינו:** `make eval-answers`: בדיקות דטרמיניסטיות (סירב? ציטט? ציטוט phantom? ה-retrieval הצליח?) ואחריהן Opus כשופט עם structured output.

**‏העיקרון:** אותם 5 מקורות לכל המודלים, כדי שההבדל יהיה המודל ולא החיפוש. משתנה אחד בכל פעם.

**‏השופט:** `Verdict` של Pydantic דרך `messages.parse`, השדה `reasoning` **ראשון** (הציון נגזר מהניתוח ולא להפך), שדות קונקרטיים (`unsupported_claims`, ‏`answers_question`, ‏`bad_citations`) במקום ציון 1 עד 10, שופט עיוור וקבוע.

**‏התוויות:** ‏`correct`, ‏`partial`, ‏`unfaithful` (טענה אחת שלא במקורות מספיקה, גם אם היא נכונה על FastAPI), ‏`false_refusal`, ‏`justified_refusal`, ‏`correct_refusal`, ‏`hallucinated`.

**‏הרף, שנקבע לפני ההרצה:** ‏unfaithful עד 5%, כל השאלות בלי תשובה מסורבות, עד 2 סירובים שגויים, ‏correct לפחות 80%.

**‏התוצאות (47 שאלות, 2026-11-02, ההרצה עלתה כ-3.08 דולר, רובה שופט):**

| ‏מודל | ‏correct | ‏unfaithful | ‏$ לשאלה | ‏עובר? |
|---|---|---|---|---|
| ‏Haiku 5.5 | ‏78.6% | ‏9.8% | ‏0.0004 | ‏לא, בשני תנאים |
| ‏**Sonnet 5.5** | ‏90.5% | ‏0% | ‏0.007 | ‏כן, ונבחר |
| ‏Opus 5.5 | ‏90.5% | ‏5.0% | ‏0.016 | ‏על הגבול, פי 2.3 |

**‏מה עוד למדנו:** ‏q18 ו-q22 נכשלו בכל שלושת המודלים (`justified_refusal`): תקרת האיכות היא החיפוש. ב-q41 שני מודלים הוסיפו קוד שלא היה ב-chunks, כי הקוד חי בסעיף אחר.

**‏כיול השופט:** קראנו 3 verdicts ביד. הסכמנו עם 2. ‏Opus q27 סומן unfaithful על משפט הסבר, ולא הסכמנו. השופט קפדן, ולכן ה-5.0% של Opus כנראה גבוה מהאמת. ההחלטה לא משתנה. **3 בדיקות הן לא מדידת הסכמה**, וזה מה שהשרשור של התיוג עושה עכשיו.

**‏הטעות שלא עשינו:** לא הזזנו את הרף כדי להציל את Haiku.

## ‏שלב 2ה: שכתוב שאלה ([02ה](02e-query-rewriting.md))

**‏מה בנינו:** Haiku כותב 2 ניסוחים בשפת התיעוד, מחפשים עם המקורית ועם הניסוחים, ממזגים ב-RRF, וה-reranker מדרג מול **השאלה המקורית**. כל כשל בשכתוב מחזיר רשימה ריקה, והחיפוש ממשיך כרגיל.

**‏הקריטריונים שנקבעו מראש:** לתקן לפחות אחת מ-q18 ו-q22, אפס שבירות מול rerank, ושאלות חדשות שאתה כותב לבדיקה סופית.

**‏התוצאות, אותה פקודה פעמיים:**

| ‏הרצה | ‏hit@5 | ‏p50 | ‏מה תוקן |
|---|---|---|---|
| ‏rerank (בסיס) | ‏0.952 | ‏172ms | |
| ‏rewrite_rerank, הרצה 1 | ‏0.976 | ‏1,522ms | ‏q18 |
| ‏rewrite_rerank, הרצה 2 | ‏0.952 | ‏1,473ms | ‏כלום |

**‏ההחלטה:** נשאר opt-in. היינו מוסיפים 1.3 שניות לכל שאלה בשביל רעש.

## ‏שלב 3ג: עלות, cache ו-tracing ([03ג](03c-cost-cache-tracing.md))

**‏מה בנינו (את ארבעת החלקים כתבת ב-TDD):** ‏`SpendTracker`, ‏`AnswerCache`, ‏`GuardedPipeline` ו-`Trace`.

**‏עלות:** `(input × מחיר_in + output × מחיר_out) / 1,000,000`, מה-`usage` של כל תשובה. שאלה טיפוסית: כ-2,500 פנימה ו-300 החוצה, כ-0.008 דולר ב-Sonnet, כלומר כ-600 שאלות ב-5 דולר. טוקני thinking נספרים כ-output. ‏`cost_of` מחזיר 0 כשאין usage.

**‏תקציב יומי:** 503 עד חצות UTC. יש `threading.Lock` כי `+=` הוא שלושה צעדים (lost update). השעון מוזרק כדי לבדוק "מחר". **לא תקרה קשיחה:** `allow` לפני הקריאה ו-`record` אחריה, אז בקשות בטיסה יכולות לעבור.

**‏cache:** ‏LRU עם TTL (500 רשומות, שעה, `OrderedDict`). המפתח: שאלה מנורמלת ו-`מודל | גרסת תיעוד | top_k | מצב חיפוש`. **לא** במפתח: נוסח ה-prompt, מודל ה-embedding וה-chunking. לא שומרים NOT_FOUND. מחזירים עותק (`dataclasses.replace`).

**‏הסדר ב-GuardedPipeline:** cache קודם, אחר כך תקציב, כי hit עולה 0, וכשהכסף נגמר שאלות שכבר נענו עדיין מוגשות.

**‏tracing:** שורת JSON אחת לבקשה, גם בכישלון (`finally`): ‏`request_id` (או `X-Request-ID` שהגיע), ‏`spans_ms`, ‏`total_ms`, ‏`status`, ‏`cache_hit`, ‏`cost_usd`, ‏`model`, ‏`cited`, ‏`question_chars`. ה-pipeline כותב דרך `ContextVar` בלי לקבל את ה-trace כפרמטר. **לא** בלוג: טקסט השאלה, התשובה, מפתחות.

**‏מה לא עשינו:** Redis, ‏semantic cache ("optional" מול "required" קרובות בווקטור והפוכות בתשובה), ‏OpenTelemetry, ‏prompt caching של Anthropic (אין תחילית קבועה וארוכה).

## ‏שלב 3ה: ‏monitoring והתראות ([03ה](03e-monitoring-alerts.md))

**‏ההבדל:** לוג עונה "מה קרה לבקשה הזאת". ‏monitoring עונה "איך השירות מרגיש". התראה עונה "מתי להעיר מישהו". אנלוגיה: תיק רפואי, מד חום, ואזעקה.

**‏מה מודדים:** RED ועוד אחד: Rate, ‏Errors (5xx חוץ מ-503), ‏Duration (p95, ‏nearest rank), ו-Cost. ה-503 של התקציב נספר בנפרד (`rejected`) עם התראה משלו: הוא לא תקלה, אבל משתמשים נשארו בלי תשובה.

**‏מה בנינו:** כתבת `percentile`, ‏`summarize` ו-`check_alerts` (13 טסטים). הם עברו ל-`src/rag/logreport.py` (16 טסטים), עם `make report` שמסכם את לוגי השעה האחרונה ויוצא עם 1 אם התראה נורתה. בענן: 3 log-based metrics (‏`rag_errors`, ‏`rag_budget_rejections`, ‏`rag_latency_ms` מסוג distribution) ו-3 alert policies (יותר מ-3 שגיאות ב-10 דקות, ‏p95 מעל 8,000ms, כל 503 של תקציב) עם ערוץ מייל. הקבצים ב-`monitoring/`.

**‏נבדק מקצה לקצה (2026-11-15):** ‏`DAILY_BUDGET_USD=0.001`, שתי שאלות **שונות**, השנייה קיבלה 503, ואחרי כ-4 דקות הגיע מייל. ‏`make report` הראה `budget refused 2`. ה-incident נסגר לבד אחרי 30 דקות (`autoClose`).

**‏ההחלטות:** `min_requests` כדי ששתי בקשות ושגיאה אחת לא יהיו "50% שגיאות" בשלוש בלילה. בלי uptime check על `/ready`, כי הוא היה מעיר את ה-container ואת Neon ומבטל את החינם.

**‏הטעות:** כתבתי קודם "להתריע על קפיצה ב-reconnects". ב-Neon Free חיבור מחדש הוא רגיל אחרי כל שינה. מה שחשוב הוא שהוא מצליח, וזה מה שהתראת השגיאות בודקת. ‏**מגבלה שנשארה:** ‏503 נכלל באחוזוני ה-latency ומוריד את p50.
