# ‏שלב 3ב-1: מפתח API והגבלת קצב

## ‏1. הבעיה

‏הנקודה `POST /ask` מפעילה קריאה בתשלום ל-Claude (כ-0.7 סנט לשאלה עם Sonnet). אם ה-API חשוף לאינטרנט בלי הגנה, כל סקריפט עם לולאה יכול לשרוף את התקציב תוך דקות. אנלוגיה: ברז פתוח בלי מונה. צריך שני דברים:

1. **‏אימות (authentication):** מי אתה? אצלנו, מפתח בכותרת `X-API-Key`.
2. **‏הגבלת קצב (rate limiting):** כמה פעמים בדקה מותר לך? אצלנו, 20 לכל מפתח.

‏הקוד נמצא ב-`src/rag/security.py`, והחיבור ל-API ב-`api.py`.

## ‏2. איך זה עובד, צעד אחר צעד

<div dir="ltr">

```
בקשה ל-POST /ask
   |
   v
check_access (Depends)          <- רץ לפני הפונקציה של ה-endpoint
   |-- אין מפתח / שגוי  -> 401   (ה-endpoint לא רץ בכלל)
   |-- יותר מדי בקשות   -> 429 + Retry-After
   v
ask(...)  ->  pipeline  ->  Claude   <- רק כאן משלמים
```

</div>

‏הנקודה החשובה: **הבדיקה קורית לפני ה-pipeline**, ולכן בקשה נדחית לא עולה כלום, לא embedding ולא קריאה ל-Claude. יש בדיקה שמוכיחה זאת (`test_a_rejected_request_never_reaches_the_pipeline`).

## ‏3. קודי ה-HTTP (שאלה קלאסית בראיון)

- **‏401 Unauthorized:** חסר מפתח, או מפתח שגוי. "אני לא יודע מי אתה".
- **‏429 Too Many Requests:** חרגת מהקצב. התגובה כוללת `Retry-After`, מספר שניות להמתין.
- **‏403 Forbidden:** (לא בשימוש כאן) אני יודע מי אתה, אבל אסור לך. זה ההבדל בין אימות להרשאה.

## ‏4. שלוש החלטות בקוד

**‏א. `hmac.compare_digest` ולא `==`.** השוואת מחרוזות רגילה עוצרת בתו הראשון שונה. מי שמודד זמני תגובה יכול לנחש מפתח תו אחר תו (timing attack). `compare_digest` לוקחת אותו זמן בכל מקרה. אנחנו גם עוברים על כל המפתחות בלי לעצור מוקדם, מאותה סיבה.

**‏ב. כמה מפתחות, מופרדים בפסיק (`API_KEYS=a,b`).** כך מחליפים מפתח בלי השבתה: מוסיפים את החדש, מעבירים את הלקוחות, ומסירים את הישן (rotation).

**‏ג. חלון הזזה (sliding window).** לכל מפתח שומרים את חותמות הזמן של הבקשות האחרונות. בבקשה חדשה מוחקים חותמות ישנות מדקה, ומאשרים רק אם נשארו פחות מהמגבלה:

<div dir="ltr">

```
limit=3, window=60
t=0 ok   t=10 ok   t=20 ok   t=30 נדחה
t=61 ok  (הבקשה מ-t=0 יצאה מהחלון)
```

</div>

‏למה לא "מונה שמתאפס כל דקה"? כי אז אפשר לשלוח 20 בשנייה 59 ועוד 20 בשנייה 61, כלומר 40 בשתי שניות. חלון הזזה מונע את זה.

## ‏5. ברירת המחדל, והמגבלה שחייבים להכיר

- **‏אם `API_KEYS` ריק, האימות כבוי** (נוח לפיתוח מקומי), ומוצגת אזהרה בלוג. כשהוא כבוי, הגבלת הקצב נעשית לפי כתובת IP. בפרודקשן חייבים להגדיר אותו.
- ‏`/health` נשאר פתוח, כי Load Balancer אין לו מפתח.
- **‏המגבלה:** מוני הקצב נשמרים בזיכרון של התהליך. אם Cloud Run מריץ 3 מופעים, כל לקוח מקבל פי 3 מהמגבלה, ואתחול מאפס אותה. זה מגן על התקציב מפני לקוח רועש אחד, אבל מגבלה גלובלית אמיתית דורשת מאגר משותף (Redis) או שער (gateway) לפני השירות. את זה כדאי לומר בראיון בעצמך, לפני שישאלו.

## ‏6. תרגיל

1. ‏צור מפתח: `python -c "import secrets; print(secrets.token_urlsafe(32))"` והוסף ל-`.env` שורה `API_KEYS=<המפתח>` (לא להעלות ל-git).
2. ‏`make api`, ואז:
   - ‏`curl -X POST localhost:8000/ask -H 'content-type: application/json' -d '{"question":"What is FastAPI?"}'` מחזיר 401.
   - ‏אותה פקודה עם `-H 'X-API-Key: <המפתח>'` מחזירה תשובה.
3. ‏הוסף `RATE_LIMIT_PER_MINUTE=2` והרץ את הפקודה עם המפתח 3 פעמים ברצף. הפעם השלישית אמורה להחזיר 429.
4. ‏פתח את `localhost:8000/docs`: יש כפתור **Authorize**, שבו מזינים את המפתח ומנסים את ה-endpoint מהדפדפן.
5. ‏מה קורה אם `curl localhost:8000/health` בלי מפתח? ולמה?

## ‏7. שאלות ראיון

<details><summary><b>‏איזה קוד HTTP מחזיר ה-API שלנו כשחסר מפתח, כשהמפתח שגוי וכשעברו את המכסה, ומה ההבדל לעומת 403?</b></summary>
‏חסר מפתח או מפתח שגוי: ‏401. מכסה שנוצלה: ‏429 עם כותרת `Retry-After` (מספר שניות להמתין). ‏403 לא קיים בקוד שלנו. ההבדל: ‏401 אומר "אני לא יודע מי אתה" (אימות), ו-403 אומר "אני יודע מי אתה, אבל אסור לך" (הרשאה). היינו צריכים 403 אילו היו אצלנו הרשאות שונות למפתחות שונים (למשל מפתח קריאה בלבד), אבל לכל מפתח תקף יש אותן זכויות.
</details>

<details><summary><b>‏למה `compare_digest` ולא `==`, ולמה הלולאה עוברת על כל המפתחות ולא עוצרת כשנמצא תואם?</b></summary>
‏`==` עוצר בתו הראשון שלא תואם, אז זמן התשובה מרמז כמה תווים בהתחלה נכונים, ותוקף שמודד זמנים יכול לנחש מפתח תו אחרי תו (timing attack). ‏`compare_digest` משווה בזמן שלא תלוי בתוכן. מאותה סיבה הלולאה ב-`_valid` לא עוצרת בהתאמה ראשונה (`ok |= ...`): אחרת הזמן היה מגלה באיזה מקום ברשימה המפתח נמצא. ביושר: בפועל התקפה כזו דרך רשת עם רעש של milliseconds קשה מאוד, אבל התיקון עולה שורה אחת, ולכן עושים אותו.
</details>

<details><summary><b>‏הגבלת קצב: במה sliding window טוב יותר ממונה שמתאפס כל דקה?</b></summary>
‏במונה שמתאפס יש פירצה בגבול: עם מכסה של 20, אפשר לשלוח 20 בשנייה 59 ועוד 20 בשנייה 61, כלומר 40 בקשות בשתי שניות. ב-sliding window שומרים את חותמות הזמן של הבקשות האחרונות, ובכל בקשה מוחקים חותמות ישנות מ-60 שניות. מאשרים רק אם נשארו פחות מהמכסה, ולכן בכל חלון של 60 שניות, מכל נקודת התחלה, יש לכל היותר 20 בקשות. המחיר: זיכרון של חותמת לכל בקשה (עד `limit` חותמות לכל מפתח), לעומת מספר אחד.
</details>

<details><summary><b>‏לפי מה מגבילים קצב, ומה קורה כשהאימות כבוי או כשיש proxy לפני השירות?</b></summary>
‏כשיש מפתחות, ההגבלה היא **לפי מפתח**, כי מפתח מזהה לקוח טוב יותר מכתובת IP (הרבה לקוחות יכולים לשבת מאחורי IP אחד, ולקוח אחד יכול להחליף IP). כשהאימות כבוי (פיתוח מקומי) ההגבלה היא לפי IP. אזהרה: מאחורי load balancer או proxy, כתובת ה-IP שהשרת רואה היא של ה-proxy, ולכן כל הלקוחות ייספרו כאחד, אלא אם קוראים את הכתובת האמיתית מ-`X-Forwarded-For` ומאמינים רק ל-proxy שאנחנו שולטים בו. זו עוד סיבה שבפרודקשן חייבים להפעיל מפתחות.
</details>

<details><summary><b>‏הגבלת הקצב שלנו שמורה בזיכרון, ו-Cloud Run מריץ 3 מופעים. מה בדיוק קורה, ומה הפתרונות?</b></summary>
‏לכל מופע מונים משלו, ולכן לקוח שהבקשות שלו מתפזרות בין המופעים יכול לקבל עד פי 3 מהמכסה (עד 3 × `RATE_LIMIT_PER_MINUTE`), ובכל הפעלה מחדש של מופע המונים מתאפסים. עדיין יש הגנה: כל מופע בודד חוסם לקוח שמגזים. פתרונות לגבול גלובלי: מאגר משותף (Redis עם חלון נע או token bucket), או הגבלה ברמת ה-API gateway / load balancer לפני השירות.
</details>

<details><summary><b>‏איזו בקשה לא מוגבלת בקצב אצלנו, ומה הסיכון?</b></summary>
‏בקשה עם מפתח שגוי. ‏`Guard.check` דוחה ב-401 **לפני** שהוא מגיע להגבלת הקצב, כלומר ניחושי מפתחות לא נספרים נגד אף מכסה, ותוקף יכול לנסות כמה שירצה (ל-`secrets.token_urlsafe(32)` זה חסר סיכוי מעשי, אבל בתור עיקרון זו חולשה). התיקון: להגביל גם ניסיונות כושלים לפי IP, או לתת ל-gateway לעשות את זה.
</details>

<details><summary><b>‏איך מחליפים (rotation) מפתח API בלי להשבית לקוחות?</b></summary>
‏`API_KEYS` מקבל כמה מפתחות מופרדים בפסיק. שלבים: (1) מוסיפים את החדש לצד הישן (`old,new`) ופורסים; (2) מעבירים את הלקוחות למפתח החדש; (3) אחרי שהתנועה עם הישן ירדה לאפס, מסירים אותו ופורסים שוב. מפתח שדלף מסירים מיד, גם במחיר של השבתת הלקוח שהשתמש בו. הערה: מוני הקצב הם לפי מפתח, ולכן בזמן ה-rotation כל לקוח מקבל מכסה נפרדת לכל אחד משני המפתחות.
</details>

## ‏8. מה עדיין לא כאן

- ‏הגנה מפני **prompt injection** (טקסט במסמכים או בשאלה שמנסה לשנות את ההוראות של המודל): החלק הבא, 3ב-2.
- ‏מפתח שונה לכל לקוח עם מכסה משלו, ומגבלת הוצאה יומית כוללת: שלב העלות.
